# mem0 记忆机制:设计与实现思想

> 本文讲 mem0 **为什么**这么做,不逐行讲代码。读完后你应该能预测:面对一个新场景,mem0 会怎么处理。

---

## 核心洞察:记忆是"蒸馏",不是"存储"

很多人把"AI 记忆"理解成"把聊天记录存起来,下次检索回去"。mem0 的第一个、也是最重要的设计决定就是**拒绝这个理解**。

在 mem0 里,记忆的写入不是 `存原文`,而是:

> 对话进来 → LLM 把它**蒸馏成若干条原子事实** → 每条事实是一个自包含的、可独立检索的句子 → 存这个,不存原文。

比如用户说"我上周和 Max 去巴黎露营了,徒步加游泳,累但开心",mem0 不会存这句话,而是抽出类似"用户上周和 Max 去巴黎露营""用户喜欢徒步和游泳""用户有一只叫 Max 的伙伴"这样的事实。

为什么必须是"蒸馏"而不是"存原文"?三个理由:

1. **原文有噪音**:寒暄、客套、自我修正、跑题,全是稀释信号。检索时一句"我喜欢深色模式"远比一段含这句话的对话好匹配。
2. **原文不可去重**:用户说过三次"我喜欢深色模式",原文三次都不同,无法判同。蒸馏成同一句事实后才能去重。
3. **原文不可累加**:用户今天说"喜欢披萨",下月说"喜欢披萨和寿司",原文是两条独立记录,但记忆应该**演进**成"喜欢披萨和寿司"。只有蒸馏成原子事实后,才能在事实层面合并/更新。

这个洞察决定了 mem0 的一切后续设计:它**不是个数据库,是个记忆蒸馏管道**。LLM 在这里既是消费者(应用读写记忆),也是蒸馏器(写入时抽取事实)。

---

## 设计原则

### 1. 事实是记忆的原子单位,且必须自包含

一条记忆必须脱离上下文也能被理解。"他上周去了巴黎"不是合格记忆——"他"是谁?"上周"是哪周?mem0 的抽取 prompt 强制要求:代词消解掉,相对时间锚定成绝对日期("用户于 2023-05-15 那周去了巴黎")。

**思想**:记忆会被独立检索、独立拼回上下文。任何依赖原始对话上下文才能理解的记忆,在半年后检索出来都是垃圾。所以写入时就**把上下文烙进每条记忆本身**。

### 2. LLM 只做"理解",确定性逻辑做"管理"

这是 mem0 V3 最关键的一次设计转向,也是看代码最容易踩坑的地方。

**老版本**:写入时让 LLM 对每条事实做四选一决策——`ADD / UPDATE / DELETE / NOOP`。把"该不该存、要不要改、要不要删"全交给 LLM 判。

**V3**:LLM **只负责抽取事实(只 ADD)**,去重和增删改由确定性逻辑承担——文本 md5 完全一致就跳过,要改要走显式的 `update()` API。

为什么往回退?

- **LLM 决策不可控**:它会编造不存在的记忆 ID 去做"UPDATE",会把"语义相似但事实不同"判成重复删掉,会随机性删掉该留的。这些在生产里是灾难。
- **费 token**:四选一决策要把全部已有记忆喂给 LLM 让它逐一比对,而增量抽取只需要它"看着已有的,别重复抽"。
- **不可复现**:同样的对话跑两遍,LLM 决策可能不同,记忆库状态就漂移。

所以设计原则是:**把需要"理解"的事(从对话里识别事实)交给 LLM,把需要"确定性"的事(去重、ID 管理、时序)交给代码**。不要让概率模型做判断题。

> 那 `ADD/UPDATE/DELETE/NOOP` 那套 prompt 还在不在?上游 V3 还留着做历史兼容,但写入主路径早不调它了;本清理分支干脆物理移除了(见 `mem0-v3-optimal-path-guide.md`)。网上很多讲 mem0 的旧文还在讲那套四操作决策——跟当前实现对不上了。

### 3. 上下文驱动的"增量"写入

LLM 抽取事实时,不是只看本次新消息。喂给它的输入有四块:

- **本次新消息**——抽取对象
- **已有的相关记忆**(向量召回 top 10)——让它知道"已经记过什么",别重复抽
- **本 session 最近抽过的事实**——短时去重
- **最近几轮对话 + 观察日期**——解代词、锚定时间

**思想**:写入记忆不是孤立事件,是**"在已有记忆的累加上增量补事实"**。给抽取器看历史,它才能判断"这条是新信息还是旧信息的重复"。没有上下文的抽取必然产生大量重复,把去重压力全压在 hash 上(hash 只能挡完全一致,挡不住语义重复)。

这其实是个分工:hash 挡"完全一样",prompt 挡"语义重复",两层一起才够。

### 4. 三层存储,各司其职

mem0 的记忆分布在三个地方,没有任何一个能独自完成所有查询需求:

| 层 | 存什么 | 擅长 | 不擅长 |
|----|--------|------|--------|
| **向量库** | 记忆本体(事实文本 + 向量) | 语义相似检索 | 精确关联、时序追溯 |
| **实体库** | 实体→记忆的反向索引 | 精确按实体查、跨记忆关联 | 语义模糊、长文本 |
| **SQLite** | 变更历史(ADD/UPDATE/DELETE 轨迹)+ 最近消息 | 时序、可追溯 | 语义检索 |

为什么不全塞进一个库?因为**查询模式决定存储**:

- "找和'用户喜欢什么运动'相关的记忆"——要语义,得向量库。
- "找所有提到'巴黎'的记忆"——要精确,得实体索引。
- "这条记忆是怎么演变的"——要时序,得历史表。

向量库做不好精确(近似召回会漏会错),实体库做不好语义(实体是离散词),SQLite 做不好相似(它是行存的)。与其在一个库里硬凑,不如按查询模式分库,各自最优。

mem0 的实现巧在一个地方:**实体库就是同一个向量库里的另一个 collection**,复用了向量库的基础设施和 embedder,没有引入新组件。这是"够用就好"的克制——它没为了图式查询上 Neo4j(那是个可选的重路径)。

### 5. 实体关联:用最小机制实现,不过度工程化

mem0 有"图式"能力——记忆之间通过实体关联,检索时命中实体的记忆会被加权。但它**没在主路径用图数据库**:

- 抽实体用 **spaCy**(本地 NLP,不是 LLM),得到人名/地名/引号词/复合名词短语
- 实体也存成向量(实体文本的 embedding),payload 里带一个 `linked_memory_ids` 列表
- 关联合并:文本完全一致就合并,否则语义相似度 ≥0.95 视为同一实体

**思想**:90% 的"实体关联检索"需求,用"向量召回实体 + 反向索引到记忆"就够。真上图数据库要引入新依赖、写 Cypher、维护图 schema,复杂度跳一档,而收益对大多数场景边际。mem0 选了**能解决问题的最简机制**,把图数据库留作可选路径。

这是一个可复用的设计判断:**先问"这个能力是不是必须上重武器",能复用现有基础设施就复用**。

### 6. 和 LLM 交互的纪律:别让它生成它生成不了的东西

一个很小的细节,但透出设计纪律:mem0 把已有记忆的真实 ID(UUID)喂给 LLM 前,会先映射成 `"0".."9"` 这样的序号,落库前再映射回去。

为什么?因为 **LLM 没法可靠生成 UUID**——它会编一个格式像但根本不存在的 ID,然后你拿着这个假 ID 去库里查,啥也查不到。给它无意义但可数的序号,它只能在你给的集合里引用,不可能凭空造。

**思想**:这是和 LLM 协作的一般原则——**不要让概率模型生成它不可能可靠生成的标识符/结构/引用**。需要确定性输出的部分(ID、格式、计数),要么你给它、要么你用确定性逻辑兜底。LLM 只产出它能产出的(自然语言、事实判断),你负责把它产出的东西"钉"到确定的结构上。

### 7. 状态与日志分离:本体可变,历史不可变

记忆本体在向量库里,是**可变状态**——可以被 update、被 delete。但每一次变化都在 SQLite 里留一条不可变的历史记录(事件类型 + 变更前后文本 + 时间)。

**思想**:这是 event-sourcing 的轻量版——**可变状态用于"当前是什么样",不可变日志用于"怎么变成这样的"**。检索要的是当前状态(走向量库),审计/回溯要的是变更轨迹(走历史)。两者分离,各自不被对方的读写模式拖累。

删一条记忆,不是从历史里抹掉,而是向量库删 point + 历史记一条 DELETE。所以 `history(memory_id)` 能还原一条记忆的完整生平。这比"在记忆上加个 deleted 标志位"干净——软删的记忆会污染检索,而历史只读不检索。

### 8. 写入是一个批处理事务,不是 N 个独立操作

V3 把一次 `add` 设计成一条流水线:一次 LLM 调用抽全部事实、一次 `embed_batch` 嵌入全部、一次 `vector_store.insert` 落库、一次实体批量链接。

老做法是"每条事实一个循环:抽一条→embed 一条→存一条→链实体",N 条事实就是 N 倍的 LLM/嵌入/DB 往返。

**思想**:把"一次对话写记忆"当作**一个事务**整体批处理,而不是 N 个独立操作。这是工程上的基本素养——**LLM 调用和 DB 往返是昂贵资源,能批就批**——但在 RAG 系统里特别容易被忽略,因为很多人把"调 LLM"当成单元操作随手循环。

### 9. 机制与基础设施解耦

记忆的核心逻辑(蒸馏、去重、增量、链接)和"存哪个库、用哪个模型"是**完全解耦**的:向量库、embedder、LLM、reranker 都是 `Factory + 抽象基类`,30 个向量库、24 个 LLM 随便换,核心逻辑不动。

**思想**:记忆**机制**和记忆**基础设施**是两个正交维度。mem0 押注的是机制(怎么抽、怎么去重、怎么关联),不押注基础设施(Qdrant 还是 Pinecone、OpenAI 还是 Anthropic)。所以它把机制写死、基础设施留接口。这是个聪明的风险隔离——基础设施会变(模型换代、库兴衰),机制是它的护城河。

## 隐含的张力与权衡

把这些设计放一起看,mem0 在几个维度上做了明确取舍:

- **精确 vs 语义**:hash 去重精确但漏语义重复;LLM 上下文兜底语义但不可靠。它选了"两层叠加,精确优先"。代价:语义级重复仍可能漏(同义不同字),只能靠 reranker 在检索侧缓解。
- **抽取质量 vs 成本**:每次 add 都调 LLM 抽取,贵但质量高。它留了 `infer=False` 的逃生口(原文直存,不抽),把选择权交给调用方。
- **简单 vs 表达力**:entity store 比 Neo4j 简单得多,但表达力弱(只能"实体→记忆"的反向索引,做不了多跳图查询)。它选了简单,把图数据库留作可选。
- **可追溯 vs 存储**:每条记忆每次变更都留历史,历史无限增长。它选了可追溯,靠一个 `prune-logs` 脚本定期清——把治理责任甩给运维。

这些取舍的共同取向:**优先选能用最简机制覆盖主流场景的方案,把重路径留作可选,把治理责任明确甩给调用方/运维**。不追求"什么都支持",追求"默认路径足够好且简单"。

## 一个心智模型带走

把 mem0 的记忆机制记成一句话:

> **LLM 当蒸馏器,把对话凝成自包含的原子事实;hash 当第一道闸挡完全重复,LLM 的上下文当第二道闸挡语义重复;事实存向量库(语义检索)、实体存另一个 collection(精确关联)、变更存 SQLite(时序追溯);三层按查询模式分库,各司其职;写入是一次批处理事务,更新删除是显式 API,不让 LLM 做确定性决策。**

抓住这句话,你就抓住了 mem0 的全部设计意图。剩下的代码细节,都是这句话的实现注脚。
