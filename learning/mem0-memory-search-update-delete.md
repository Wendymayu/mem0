# mem0 记忆机制:检索、更新、删除的设计思想

> 上一篇讲了写入与存储。这篇讲另外三个动作——`search` / `update` / `delete`——它们的设计在回答同一个问题:**怎么在向量库(擅长相似召回、不擅长精确管理)之上,做出有质量的检索和安全的变更?**

---

## 贯穿的张力

向量库的本质是"给我一个向量,我返回最像的 N 个"。它**只**擅长这一件事。但记忆系统要的远不止:

- 检索要"语义相近 **且** 提到同一实体 **且** 命中关键词 **且** 没过期 **且** 属于这个用户"
- 更新要改文本同时维护派生结构(实体链接)
- 删除要从检索消失但保留审计轨迹

向量库哪样都不直接会。所以 mem0 的检索/更新/删除,本质都是在**给向量库打补丁**——补它不擅长的精确过滤、派生维护、时序治理。理解了这点,后面的每个设计都顺理成章。

---

## 一、检索:三路召回 × 过取再排 × 过滤 × 可选重排

mem0 的检索不是"一次向量查询出 top_k",而是一条**两阶段流水线**:先**召回一个比需要大得多的候选池**,再**多信号融合打分裁剪**。

### 1. 三路召回,互相补盲

mem0 同时发三路召回,因为单一信号各有盲区:

| 召回路 | 做什么 | 擅长 | 盲区 |
|--------|--------|------|------|
| **语义(dense)** | query 向量化 → 向量检索 | 意思相近、同义改写 | 精确词、专有名词 |
| **关键词(BM25)** | query 词形归并 → 全文检索 | 精确词命中、罕见术语 | 同义、改写 |
| **实体 boost** | query 抽实体 → 查实体库 → 加权关联记忆 | 主题锚定、跨记忆关联 | 语义模糊 |

为什么非要三路?因为**任何单路都有系统性漏检**:语义路会漏掉"用户提到 `pgvector`"这种精确词(它和"数据库"向量相近但不是同一回事);关键词路会漏掉"用户喜欢散步"检索"用户爱走路"(同义不同字);实体路在 query 没有明显实体时无效。三路融合的本质是**用各自的强项补别人的盲区**——这是混合检索的经典动机,mem0 把它做到检索的默认路径里,而不是可选增强。

query 在进各路前还要预处理:词形归并(给 BM25 用,`running`→`run`)、实体抽取(spaCy,给 boost 用)。**同一个 query 被改写成三种适合三种召回的形态**——因为三路召回的最佳输入本来就不一样。

### 2. 过取再排(over-fetch then rank)

内部检索时,mem0 取的不是用户要的 `top_k`,而是 `max(top_k × 4, 60)` 的候选池,打分融合后再裁到 `top_k`。

为什么不直接取 `top_k`?因为**纯语义的 top_k 切得太早**——一条本可被关键词或实体信号救回的相关记忆,可能在纯语义排序里排在 30 名开外,直接 top_k 就把它丢了。先取一个大池子,让三路信号在池子上融合,再裁剪,才能把"语义弱但其他信号强"的相关记忆捞回来。

这是**两阶段检索**(召回 → 排序)的体现:召回阶段宁可多取(高召回率),排序阶段再精选(高精度)。两阶段各用各的逻辑,不混。

### 3. 融合打分与 threshold

三路结果进 `score_and_rank`:语义分 + BM25 分 + 实体 boost 加权,过 `threshold`(默认 0.1)挡掉低分噪音,取 `top_k`。

`threshold` 是个设计取舍:默认 0.1 很宽松(宁可多返回让上层再筛),因为"漏掉相关记忆"通常比"多返回几条"代价更大——记忆系统的误差成本不对称。

### 4. 实体 boost 的衰减巧思

实体 boost 不是"命中的实体给固定加分",而是一个衰减公式:

> boost = 实体相似度 × 权重 × `1/(1 + 0.001 × (链接记忆数 - 1)²)`

最后一项是关键:**一个实体链接的记忆越多(hub 实体,比如"用户""工作"这种泛词),它给每条记忆的 boost 越小**。

思想:hub 实体区分度低——"巴黎"链接 3 条记忆,boost 实在;"用户"链接 200 条记忆,boost 几乎为零。**稀有才值钱**,这是 TF-IDF 思想在实体层的复刻。如果不衰减,泛词实体会给一大堆记忆无差别加权,boost 就退化成噪音。

附带:实体最多取 8 个、去重、并行查(ThreadPoolExecutor,4 线程)——数量和并发都设了上限,防一个查询拖垮实体库。

### 5. 通用过滤代数

`search` 的 `filters` 不只是 `{"user_id": "u1"}`,支持一整套操作符:`eq/ne/gt/gte/lt/lte/in/nin/contains/icontains`、通配 `*`、以及 `AND/OR/NOT` 逻辑组合。

mem0 定义这套**通用查询代数**作为中间表示,每个向量库把它翻译成自己的原生 filter 方言。思想:mem0 不绑定某个库的过滤语法,定义一套"查询中间语言",各 store 适配。这是上一篇"机制与基础设施解耦"在查询层的延伸——**不只存储层可插拔,查询语义也跨库一致**。

### 6. 记忆生命周期与可解释

- **过期过滤**:`expiration_date` 标记的记忆,默认从检索隐藏,`show_expired=True` 才查。过期不是物理删,是检索时过滤——和下面删除的"历史软删"是同一思想:状态层的过滤而非物理抹除。
- **scope 强制**:`search` 必须带 `user_id/agent_id/run_id` 至少一个,**没有全局搜索**。多租户隔离在 API 层强制,不靠应用层自觉。
- **explain**:`score_details` 透出每条结果的打分构成(语义分、BM25 分、实体 boost 各占多少)。检索不是黑盒,可调试。

### 7. 可选 rerank:召回与精排分阶段

融合打分后,还能再过一道独立 `reranker`(Cohere/HuggingFace 等)。思想:**召回用向量(快、宽),精排用专门模型(慢、准)**,两阶段各用各的工具。reranker 是可选的——小数据集融合分够用,大数据集或高精度场景才上。

## 二、更新:取 → 克隆 → 改 → 覆写

更新的核心机制就四个字:**取-克隆-改-覆写**。它不是"原地改某个字段",而是先把旧 point 整个取出来,在副本上改,再用新 point 整体替换旧 point。

### 一个具体例子

假设向量库里有一条记忆 `mem_123`,内容是"用户喜欢奶酪披萨",它的 point 长这样:

```
id:      mem_123
vector:  [0.12, -0.05, ...]          ← "用户喜欢奶酪披萨" 的 embedding
payload: {
  data:            "用户喜欢奶酪披萨"
  hash:            "a1b2c3..."        ← md5(data)
  text_lemmatized: "user like cheese pizza"   ← BM25 用
  created_at:      "2026-09-01T10:00Z"
  updated_at:      "2026-09-01T10:00Z"
  user_id:         "u1"
  metadata:        {source: "chat"}
}
```

现在调 `m.update("mem_123", text="用户喜欢奶酪和鸡肉披萨")`,mem0 依次做:

**第 1 步 — 取旧 point**:`vector_store.get(mem_123)`,拿到上面的 payload + 旧向量。**没有旧 point 就直接报错**(memory_id 不存在),不会静默创建。

**第 2 步 — 克隆旧 payload**:把旧 payload 整个 deepcopy 一份当草稿(`new_metadata`)。这一步是关键——**所有你没改的字段都原样保留**,mem0 不会替你重置它们。

**第 3 步 — 在草稿上改该改的**:

| 字段 | 改成什么 | 为什么 |
|------|----------|--------|
| `data` | 新文本"用户喜欢奶酪和鸡肉披萨" | 你要改的内容 |
| `hash` | `md5(新文本)` 重算 | 文本变了,去重指纹必须跟着变 |
| `text_lemmatized` | 重新词形归并新文本 | BM25 索引要跟新内容同步 |
| `updated_at` | 当前时间 | 改动时间戳刷新 |
| `created_at` | **不动**,还是原值 `2026-09-01` | 记忆的"出生时间"不变 |
| `user_id` 等 | **不动** | 身份键,见下文 |

**第 4 步 — 重新 embed**:把新文本喂给 embedder,拿到新向量。旧向量作废。

**第 5 步 — 覆写**:`vector_store.update(mem_123, vector=新向量, payload=new_metadata)`。向量库的 update 语义就是**用新 point 替换同 id 的旧 point**——`mem_123` 现在指向新文本和新向量,旧的就没了。

**第 6 步 — 记历史**:SQLite 写一条 `UPDATE` 事件,**同时存 old 和 new 两个文本值**:

```
memory_id: mem_123
old_memory: "用户喜欢奶酪披萨"      ← 变更前
new_memory: "用户喜欢奶酪和鸡肉披萨" ← 变更后
event:      UPDATE
created_at: 2026-09-01T10:00Z      ← 沿用记忆出生时间
updated_at: 2026-09-17T...         ← 本次改动时间
```

所以 `history(mem_123)` 能看到"从 X 改成了 Y",不只是"改过"。

**第 7 步 — 文本变了,实体重链**(两步,因为 `text_changed=True`):

- **摘旧**:遍历实体库,从所有 `linked_memory_ids` 里含 `mem_123` 的实体把它摘掉。比如旧文本抽出的"奶酪披萨"这个实体原本链着 `mem_123`,现在断开。
- **重抽**:从新文本"用户喜欢奶酪和鸡肉披萨"重新用 spaCy 抽实体(可能抽出"鸡肉披萨""奶酪"),upsert 进实体库,把 `mem_123` 链到这些新实体上。

为什么是"摘旧 + 重抽"两步全量重算,不是增量改?因为**实体是文本的派生物**——旧文本的实体和新文本的实体可能完全不同(加了"鸡肉"),没法增量对齐,只能清掉旧的、重算新的。

### 几个关键设计

**为什么必须先取再覆写,不能原地改?** 因为向量库的 update 语义是"整 point 替换",你给它什么 payload 它就存什么。如果 mem0 不先把旧 payload 取出来克隆,就不知道那些"你没传的字段"(比如 `created_at`、`user_id`、`metadata.source`)原本是什么,覆写时就会丢。"取-克隆"这一步是为了**保住你没改的字段**——它是防御性的,防止部分更新变成误删字段。

**created_at 保留,updated_at 刷新**:记忆有两个时间戳。更新只动 `updated_at`,**`created_at` 永远是它第一次被 ADD 的时间**。这让一条记忆保持身份连续性——它还是"那条"记忆,只是内容变了;而不是"一条新记忆覆盖了旧的"。`history()` 能串起它的演变,靠的就是 `created_at` 这个不变的锚。

**metadata 是合并,身份键被剥离**:你传的 `metadata` 是 **merge** 进旧 payload 的(只覆盖你传的 key,不动其他);但 `user_id/agent_id/run_id/actor_id` 即使你传了也会被 `_strip_identity_keys` 拆掉忽略。前者允许你局部改属性,后者强制身份不可变——思想:**内容属性可改,归属身份不可改**。改归属等于换了"这是谁的记忆",那不是更新是新建,mem0 不让你在 update 里偷偷干这事。

**只改 metadata 的轻量路径**:如果调 `update(mem_123, metadata={confidence: 0.9})` 而不传 `text`,走的是轻量分支——**不重 embed、不重链实体、`hash/text_lemmatized` 都不动**,只 merge metadata + 刷 `updated_at` + 记 UPDATE 历史。因为文本没变,派生物(向量、实体)就不需要动。**改文本是重操作(重 embed + 重链实体),改 metadata 是轻操作**——两种更新代价差很多,API 用同一个入口,内部分流。

**这是显式 API,不是写入时自动判 UPDATE**。呼应上一篇的核心:V3 的 `add` 只 ADD,不做 UPDATE 决策。要改记忆,必须显式调 `update`。设计上把"写入新信息"(LLM 驱动的增量抽取)和"修改已有信息"(确定性 mutation)分成两个动作——前者是概率性的理解,后者是确定性的覆写,不混在一起,各自的语义和代价清晰。

## 三、删除:本体硬删,历史软删,实体清理

`delete(memory_id)` 做的事:`vector_store.delete`(硬删 point)→ SQLite 记 `DELETE` 历史(`is_deleted=1`)→ 从实体库摘掉这个 memory_id 的引用(非致命)。

### 1. 向量库硬删 + 历史软删

记忆从向量库**物理消失**(不再污染检索),但 SQLite 里留一条 `DELETE` 事件(可审计、可回溯)。

思想:**"从检索消失"和"从记录消失"是两件事**。检索要的是当前态,硬删保证它干净;审计要的是轨迹,软删历史保证它完整。这比"加个 deleted 标志位软删记忆本身"干净——软删的记忆会持续污染检索(每次查询都要过滤),而把删除信息放历史表,检索完全不碰它。

### 2. 实体清理:最终一致,非强一致

删除时从 `linked_memory_ids` 里摘掉这个 memory_id,但**失败不回滚、不报错**(non-fatal)。

思想:实体是反向索引,被指向的记忆删了,索引该维护一致性。但 mem0 选**最终一致**而非强一致——实体清理失败就让它失败,下次检索时实体 boost 会自然降权一个指向已删记忆的实体(因为那记忆已不在候选池)。强一致要加事务、加重试、加锁,对"辅助加权"这个功能过重。**按数据的重要性分一致性等级**:记忆本体要强一致,实体这种辅助索引最终一致就够。

### 3. delete_all 的防御性批处理

`delete_all(user_id=...)` 不是一条 SQL 删完,而是循环:**列一批 → 删一批 → 再列 → 再删**,直到列空。还用 `seen_batches` 记录已删的批次,如果连续两批完全一样就停。

为什么这么小心翼翼?因为向量库的 `list()` 通常有默认上限(比如 100 条),直接 `list + delete_all` 会**静默截断**——你以为删了全部,其实只删了前 100。而且删的过程中列表会变,可能出现"删了一半再列,又列到刚删的"的循环。mem0 用批 + 去重 + 重复检测兜底,在不可靠的 list/delete 语义上做防御。

思想:**不要信任底层存储的批量语义,按最坏的语义做防御性设计**。这种"看起来简单其实暗坑"的操作,防御性循环比一条优雅的批量命令可靠。

### 4. scope 强制,reset 才全删

`delete_all` 也要求至少一个 scope 过滤;要删全部用 `reset()`。和 search 一样的多租户强制——**绝不允许一条命令误删别人的记忆**。把"删全部"做成一个独立、显眼、不可误触的动作(`reset`),而不是 `delete_all()` 的空参数默认行为。

## 四、history:读变更日志

`history(memory_id)` 从 SQLite 读这条记忆的完整事件链:`ADD → UPDATE → UPDATE → ... → DELETE`。

思想:本体可变、日志不可变。`search` 给当前态,`history` 给演变态。一条记忆被当成**有生平的对象**——不只是"现在是什么",还有"怎么变成这样的"。这是 event-sourcing 的读取侧:状态查询走快照(向量库),演变查询走事件日志(SQLite)。

---

## 五、综合心智模型

把四个动作放一起看,几条设计主线贯穿始终:

1. **两阶段检索**:召回(过取,高召回)→ 排序(融合分,高精度)→ 可选 rerank(精排)。三路信号(语义/关键词/实体)在候选池上融合,各补盲区。
2. **状态与日志分离**:向量库是可变当前态(检索/更新/删除都指向它),SQLite 是不可变事件日志(ADD/UPDATE/DELETE 全留痕)。`search` 读状态,`history` 读日志。
3. **机制与基础设施解耦**:通用过滤代数(中间表示)让查询语义跨 30 个向量库一致;存储和查询都不绑方言。
4. **多租户 scope 在 API 层强制**:search/delete_all 都必须带 scope,没有全局操作。隔离不靠自觉。
5. **按重要性分一致性等级**:记忆本体强一致(更新即同步实体),实体辅助索引最终一致(清理失败容忍),删除防御性批处理(不信任底层批量语义)。
6. **显式 mutation**:更新和删除都是显式 API,V3 不让 LLM 在写入时自动决策 UPDATE/DELETE(那条路 legacy 了)。确定性操作走确定性入口。

---

## 一句话带走

> **检索 = 三路召回(语义/关键词/实体)过取再排,融合分 + threshold + 可选 rerank,通用过滤代数 + scope 强制 + 过滤 + 可解释;更新 = 取-克隆-改-覆写(整 point 替换,保住没改的字段),created_at 不动 / updated_at 刷,memory 不存在即报错,metadata 合并但身份键剥离,文本变则实体摘旧重抽(全量重算派生物),metadata-only 走轻量路径;删除 = 本体硬删(检索干净)+ 历史软删(审计完整)+ 实体最终一致清理 + 防御性批处理。贯穿主线:状态(向量库可变)与日志(SQLite 不可变)分离,机制与基础设施(查询代数)解耦,多租户 scope 在 API 层强制,按重要性分一致性等级。**
