# mem0 agent 记忆:两个关键问题的解法

> 这是把"用 mem0 做 agent 记忆"时最容易卡住的两个实操问题的结论。配套设计原理见同目录 `mem0-memory-write-storage.md`。

---

## 问题一:mem0 底层会对传入的 messages 蒸馏吗?

**会,默认就蒸。**

调用 `memory.add(messages, user_id=...)` 时,`add` 的 `infer` 参数默认为 `True`。这个参数的意思是"是否用 LLM 从消息里抽取事实"。默认路径下,mem0 不会把 `messages` 原样存进向量库,而是走 `ADDITIVE_EXTRACTION_PROMPT` 增量抽取流水线:LLM 把对话拆成若干条自包含的原子事实,**存进向量库的是这些蒸馏后的事实,不是原句**。

举例:传入"我喜欢用 Java 开发后端服务,最近在学习 AI Infra。"mem0 大概率抽出两条事实分别入库——"用户喜欢用 Java 开发后端服务""用户最近在学习 AI Infra"。原句则被写进 SQLite 的 messages 表,作用是给**下一次** `add` 当上下文(解代词、防重复抽取),**不参与语义检索**——所以你之后 `search` 搜不到原句,只能搜到蒸馏后的事实。

### 两个旋钮

- `infer=True`(默认):蒸馏,存事实。绝大多数场景用这个。
- `infer=False`:不蒸馏,原句直接 embed 存进向量库。逃生口,留给"我就要原样存、不希望 LLM 改写"的场景(日志、凭证式记录、原始证据)。

### 设计缘由

这是 mem0 最核心的设计取舍:**可被语义检索的记忆 = 蒸馏后的事实;原对话只保留为抽取上下文**。选蒸馏而非存原文,是为了去噪音(寒暄/客套/自我修正稀释信号)、可去重(同一事实的不同说法能归并)、可演进(用户偏好变化能在事实层面合并更新)。详见设计文档第 1 节。

### 实操

- 默认 `Memory()` 用 OpenAI 做 LLM 和 embedder、本地嵌入模式的 Qdrant 做向量库、`~/.mem0/history.db` 存历史。所以**裸 `Memory()` 要跑通,环境里得有 `OPENAI_API_KEY`**——蒸馏和向量化都调 OpenAI。
- 想全本地跑(不依赖外部 API),显式配 ollama:

```python
m = Memory.from_config({
    "llm": {"provider": "ollama", "config": {"model": "llama3.1", "ollama_base_url": "http://localhost:11434"}},
    "embedder": {"provider": "ollama", "config": {"model": "nomic-embed-text"}},
})
```

### agent 记忆的标准回路

```
agent 一轮对话结束 → add(本轮对话, user_id)     ← 这里蒸馏
                  → 向量库存下原子事实
下一轮开始前      → search(query=当前意图, user_id) ← 召回相关事实
                  → 把事实塞进 agent 的 system prompt / 上下文
```

所以 agent 记忆里存的是"蒸馏过的事实",不是"聊天记录"——agent 检索时拿到的是干净结论。

## 问题二:ReAct 过程中什么时候调 `add()`?

**难点不在 mem0,在"记忆边界"的设计。** mem0 只提供 `add/search/update/delete` 原语,什么时候调 `add` 完全留给应用层决定——这是它的关注点分离:mem0 是记忆引擎,不是 agent 控制器。

### 为什么不能每轮 ReAct 都 add

不光是浪费,是**根本不匹配**:

- **蒸馏器抽错东西**:mem0 的抽取 prompt 按**对话**设计,输入是 `user/assistant` 消息。ReAct 里是 `Thought/Action/Observation` 脚手架——中间推理、工具调用管道、失败尝试、探索性死胡同。喂进去,LLM 会忠实地从"Thought: 我试试用 grep 搜一下"里抽出"agent 用 grep 搜索"这种瞬时噪音当持久事实存下来。
- **白付抽取税**:每次 `add` 至少一次 LLM 调用 + 一批 embed。ReAct 动辄十几步,成本和延迟都炸。
- **记忆库被污染**:检索时召回一堆脚手架碎片,信号被淹没。

所以问题不是"每轮 add 太频繁",而是 **ReAct 内部步骤根本不该进 `add`**。

### 真正的写入单位:轮次边界,不是推理步骤

`add` 该发生在 **agent 给用户回复的那一刻**,喂进去的是:

```
{用户这一轮说的话} + {agent 最终给用户看的回复}
```

**中间的 Thought/Action/Observation 全部跳过。** 轮次边界的内容里也有噪音(寒暄、客套),但 **mem0 的蒸馏本身就是噪音过滤器**——LLM 抽取时会自然忽略"你好""好的"这类。

关键认知:**去噪是 mem0 的活(靠 LLM 抽取完成),你的活是控制喂进去的作用域**——喂对话,不喂脚手架。很多人搞反了,在 `add` 前写一堆规则去清洗对话,其实蒸馏这一步已经做了。你不需要预过滤对话内容,只需要喂对作用域。

### "什么时候写"的三种模式

按推荐顺序:

**A. 轮次边界(环境捕获,默认兜底)**
agent 每次给用户回完话,自动 `add(本轮对话, user_id)`。简单、覆盖全、不依赖 agent 自觉。缺点:仍会捕获一些低价值轮次(闲聊),但配合蒸馏的去重 + 增量上下文,重复和闲聊基本被挡住。

**B. 显式记忆工具 `remember(事实)`**
给 agent 一个可调用的工具,让它自己决定什么值得记。agent 识别出高信号点(用户偏好、决策、承诺、被纠正的错误)时主动调一次。稀疏、高信号、agent 策展,质量最高。缺点:agent 会漏调或乱调,得靠 prompt 约束("只在出现持久性事实时调用,不要存当前任务进度")。

**C. 事件触发**
只在特定事件发生时写:用户陈述偏好、agent 做了决策、任务完成、错误被纠正、目标达成。用一个轻量分类器/规则识别"事件类型",命中才 `add`。最精准但最需要领域建模。

**推荐组合:A + B**。A 兜底保证不漏,B 让 agent 主动策展高价值点。两条路径互补:A 是 ambient,B 是 deliberate。这恰好对应 mem0 抽取 prompt 的两种形态:对话式抽取(A)和 agent 视角抽取(B,V3 用 `ADDITIVE_EXTRACTION_PROMPT` + `AGENT_CONTEXT_SUFFIX` 后缀;旧的独立 `AGENT_MEMORY_EXTRACTION_PROMPT` 已在清理分支移除,见 `mem0-v3-optimal-path-guide.md`)。

### 进阶:把"采集"和"蒸馏"解耦

ReAct 过程中**只缓存,不蒸馏**,把原始轮次攒着,到 session 结束(或后台批处理)再一次性喂给 `add`。这把"便宜的采集"和"昂贵的理解"分开——采集可以高频(几乎零成本,就是存 SQLite),蒸馏低频批量(一次 LLM 调用抽一整段)。

mem0 的 `add` 天然支持这个:`new_messages` 可以是一整段多轮对话,抽取会跨轮做增量(它内部已经取最近消息当上下文)。所以不必逐轮 `add`,攒一段再 `add` 也行,蒸馏质量甚至更高(跨轮上下文更全)。

### 针对你的 ReAct agent 的具体建议

1. **ReAct 内部绝不调 `add`**——Thought/Action/Observation 是临时态,不进记忆库。
2. **轮次结束(agent 回复用户时)调一次 `add`**,传入本轮 user 消息 + agent 最终回复。环境捕获兜底。
3. **可选:加一个 `remember(text)` 工具**,让 agent 在识别到"这是用户偏好/重要决策"时显式存。prompt 里约束"只在出现持久性事实时调用,不要存当前任务进度"。
4. **别预清洗对话内容**——把去噪交给 mem0 的蒸馏,你只控制"喂对话而非喂脚手架"这个作用域。
5. agent 轮次很密时,考虑**攒几轮再批量 `add`**,而不是每轮必 `add`。

---

## 一句话总括

> 问题一:mem0 默认就蒸馏(`infer=True`),存的是事实不是原文;原句只留作抽取上下文。
> 问题二:`add` 的单位是**对话轮次**,不是 ReAct 步骤;ReAct 脚手架绝不进 `add`;去噪交给蒸馏,你的职责是喂对作用域;推荐"轮次边界兜底 + 显式 `remember()` 工具策展"的组合。
